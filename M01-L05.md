### Урок M01-L05: Компиляция, запуск, dotnet run/build / Compilation, running, dotnet run/build

**Время / Time:** 30 мин теория + 45 мин практика

#### Теория / Theory

Компиляция превращает текст программы в исполняемый код. Представьте рецепт на русском языке: сам по себе духовка его не поймёт. Нужен переводчик-повар, который превратит текст в последовательность команд для духовки. В .NET этим «переводчиком» выступает компилятор Roslyn, а «духовкой» — среда CLR (Common Language Runtime).

Цепочка сборки в .NET состоит из двух этапов. Сначала исходный код C# компилируется в IL (Intermediate Language) — промежуточный байт-код, который сохраняется в файлах `.dll`/`.exe`. Затем уже во время запуска JIT-компилятор (Just-In-Time) превращает IL в машинный код конкретного процессора. Такое двухэтапное устройство даёт переносимость: один и тот же `.dll` работает на Windows, Linux и macOS.

Основная команда сборки — `dotnet build`. Она компилирует проект и кладёт результат в каталог `bin/<Конфигурация>/<TargetFramework>/`, например `bin/Debug/net8.0/`. Там окажутся: скомпилированная сборка `MyApp.dll`, файл отладочных символов `MyApp.pdb`, конфигурация времени выполнения `MyApp.runtimeconfig.json` и карта зависимостей `MyApp.deps.json`. По умолчанию используется конфигурация **Debug**.

Команда `dotnet run` — это «собери и сразу запусти». Она удобна для быстрой локальной разработки: изменил код — нажал Run — увидел результат. Под капотом `run` сначала вызывает `build` (если сборка устарела), а затем запускает собранную сборку без явного указания пути. Передать аргументы приложению можно через `--`: `dotnet run -- hello`.

Восстановление пакетов выполняет `dotnet restore`. Он читает файл проекта (`.csproj`) и скачивает указанные NuGet-пакеты в глобальный кэш. Начиная с .NET Core 3.0, `restore` выполняется неявно перед `build` и `run`, поэтому вручную его вызывают реже — например, в CI-конвейерах или после изменения состава зависимостей, когда нужно явно проверить, что всё скачалось.

Конфигурации **Debug** и **Release** определяют, как компилировать. Debug отключает оптимизации и сохраняет отладочные символы: по коду удобно шагать отладчиком, переменные не «пропадают». Release включает оптимизации: приложение работает быстрее, бинарник меньше, но отладка затруднена. Переключить конфигурацию можно ключом: `dotnet run -c Release` или `dotnet build -c Release`.

Когда приложение готово к деплою, используют `dotnet publish`. Она собирает проект и копирует в выходной каталог всё необходимое для запуска на целевой машине: саму сборку, зависимости и при желании среду выполнения (режим self-contained). Результат `publish` можно переносить на сервер «как есть», в отличие от промежуточного вывода `build`.

Краткая шпаргалка: `restore` — подтянуть пакеты, `build` — скомпилировать в `bin/`, `run` — собрать и запустить локально, `publish` — подготовить к развёртыванию.

#### Theory (EN)

Compilation turns program text into executable code. Imagine a recipe written in Russian: the oven cannot read it by itself. You need a translator-chef who converts the text into a sequence of commands the oven understands. In .NET that translator is the Roslyn compiler, and the oven is the CLR (Common Language Runtime).

The .NET build pipeline has two stages. First, C# source code is compiled into IL (Intermediate Language) — an intermediate bytecode stored in `.dll`/`.exe` files. Then, at run time, the JIT (Just-In-Time) compiler turns IL into machine code for the specific CPU. This two-stage design gives portability: the same `.dll` runs on Windows, Linux, and macOS.

The main build command is `dotnet build`. It compiles the project and places the output in the `bin/<Configuration>/<TargetFramework>/` directory, for example `bin/Debug/net8.0/`. There you will find the compiled assembly `MyApp.dll`, the debug symbols file `MyApp.pdb`, the runtime configuration `MyApp.runtimeconfig.json`, and the dependency map `MyApp.deps.json`. The default configuration is **Debug**.

The `dotnet run` command means "build and run immediately". It is convenient for fast local development: edit the code, run, see the result. Under the hood, `run` first calls `build` (if the output is stale) and then launches the assembled assembly without requiring an explicit path. To pass arguments to the app, use `--`: `dotnet run -- hello`.

Package restoration is done by `dotnet restore`. It reads the project file (`.csproj`) and downloads the listed NuGet packages into the global cache. Starting with .NET Core 3.0, `restore` runs implicitly before `build` and `run`, so it is invoked manually less often — for example, in CI pipelines or after changing the dependency set, when you want to explicitly confirm everything downloads.

The **Debug** and **Release** configurations define how to compile. Debug disables optimizations and keeps debug symbols: it is easy to step through code in a debugger and variables do not "disappear". Release enables optimizations: the app runs faster, the binary is smaller, but debugging is harder. You switch configurations with a flag: `dotnet run -c Release` or `dotnet build -c Release`.

When the application is ready for deployment, you use `dotnet publish`. It builds the project and copies into the output directory everything needed to run on the target machine: the assembly, its dependencies, and optionally the runtime (self-contained mode). The `publish` result can be moved to a server as is, unlike the intermediate `build` output.

Quick cheat sheet: `restore` — pull packages, `build` — compile into `bin/`, `run` — build and run locally, `publish` — prepare for deployment.

#### Пример кода / Code Example

```csharp
// M01-L05: Демонстрация сборки и запуска / Build & run demo
// .NET 8 / C# 12 — top-level statements (точка входа без явного Program.Main)
// Запуск / Run:  dotnet run -- Student ru
//                 dotnet run -c Release -- Student en

using System.Reflection;

// Необработанные строковые литералы (raw string literals, C# 11+)
// Raw string literals — удобно для многострочного баннера / handy for a banner
var banner = """
    ───────────────────────────────────────
      dotnet run / build — Demo
    ───────────────────────────────────────
    """;
Console.WriteLine(banner);

// Конфигурация сборки определяется на этапе компиляции через символы DEBUG/RELEASE
// Build configuration is fixed at compile time via DEBUG/RELEASE symbols
#if DEBUG
    const string BuildConfig = "Debug";   // отладка: символы, без оптимизации
#else
    const string BuildConfig = "Release"; // релиз: оптимизации включены
#endif

Console.WriteLine($"Конфигурация / Config : {BuildConfig}");
Console.WriteLine($".NET Runtime          : {Environment.Version}");
Console.WriteLine($"ОС / OS               : {Environment.OSVersion}");
Console.WriteLine($"Сборка / Assembly     : {Assembly.GetExecutingAssembly().Location}");

// Списковые шаблоны (list patterns, C# 11+) по аргументам командной строки
// List patterns over command-line arguments
if (args.Length == 0)
{
    Console.WriteLine("Подсказка / Hint: dotnet run -- <имя> [ru|en]");
    return;
}

var message = args switch
{
    [string name, "ru"] => $"Привет, {name}! Сборка прошла успешно.", // ветка RU
    [string name, "en"] => $"Hello, {name}! Build succeeded.",         // ветка EN
    [string name, ..]   => $"Привет/Hello, {name}!",                   // значение по умолчанию
    _                   => "Неизвестные аргументы / Unknown args"
};

Console.WriteLine(message);
```

#### Best Practices

- Запускай локальную разработку через `dotnet run`, а финальную сборку для проверки — через `dotnet build -c Release`, чтобы сразу видеть эффект оптимизаций.
- Use `dotnet run` for the inner dev loop, but validate with `dotnet build -c Release` before committing so optimization-related errors surface early.
- Не коммить каталоги `bin/` и `obj/` — они产物ы сборки; добавь их в `.gitignore`.
- Add `bin/` and `obj/` to `.gitignore` — they are build artifacts, not source.
- Для деплоя используй `dotnet publish -c Release` и осознанно выбирай framework-dependent или self-contained режим.
- For deployment use `dotnet publish -c Release` and make a deliberate framework-dependent vs. self-contained choice.

#### Частые ошибки / Common Mistakes

- Забыли `--` перед аргументами: `dotnet run hello` → флаг интерпретируется самой CLI, а не приложением. Используй `dotnet run -- hello`.
- Forgetting `--` before arguments: `dotnet run hello` → the flag is consumed by the CLI, not the app. Use `dotnet run -- hello`.
- Запускают `bin/Debug/net8.0/MyApp.exe` напрямую, но меняют код и удивляются, что ничего не обновилось. Либо `dotnet run`, либо явный `dotnet build` перед запуском.
- Running `bin/Debug/net8.0/MyApp.exe` directly, editing code, and wondering why nothing changed. Either `dotnet run` or explicitly `dotnet build` before launching.
- Тестируют только Debug и получают сюрпризы в Release (например, удалённый вызов из-за оптимизации). Всегда прогоняй сборку в Release перед релизом.
- Testing only Debug and getting surprises in Release (e.g. a call optimized away). Always run a Release build before shipping.
- Путают вывод `build` (`bin/Debug/net8.0/`) с выводом `publish` (`bin/Release/net8.0/publish/`). Деплой — только из `publish`.
- Confusing `build` output (`bin/Debug/net8.0/`) with `publish` output (`bin/Release/net8.0/publish/`). Deploy only from `publish`.
