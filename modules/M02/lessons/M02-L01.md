### Урок M02-L01: Значимые и ссылочные типы, stack vs heap / Value vs Reference Types, Stack vs Heap

**Время / Time:** 30 мин теория + 45 мин практика

#### Теория / Theory

В C# все типы делятся на две большие категории: **значимые (value types)** и **ссылочные (reference types)**. Понимание разницы между ними — фундамент для эффективной работы с памятью, производительностью и предсказуемым поведением кода.

**Значимые типы** включают все числовые примитивы (`int`, `double`, `bool`, `char`), перечисления (`enum`) и структуры (`struct`, в том числе `DateTime`, `Guid`, кортежи). Переменная значимого типа хранит сами данные напрямую. При присваивании одной переменной другой создаётся **побитовая копия** — две независимые переменные с одинаковым содержимым. Значимые типы обычно живут в **стеке (stack)**, когда это локальные переменные, либо **inline** — прямо внутри содержащего их объекта, если это поле ссылочного типа. Главное свойство — копирование по значению.

**Ссылочные типы** — это `class`, `interface`, `delegate`, `array`, `string` и `object`. Переменная ссылочного типа хранит не сами данные, а **адрес** в управляемой куче (heap), где данные реально лежат. При копировании копируется ссылка, а не объект: две переменные указывают на один и тот же объект в куче. Изменение через одну переменную видно через другую.

**Аналогия «ценная бумага vs адрес сейфа».** Значимый тип — как ценная бумага, которую вы держите в руках: передавая её коллеге, вы отдаёте оригинал (точнее, точную копию), и у вас остаётся ваш экземпляр, независимый от его. Ссылочный тип — как адрес банковского сейфа: вы можете раздать адрес десяти людям, но сейф один; кто угодно с адресом может положить туда деньги, и все остальные это увидят.

**Стек и куча.** Стек — быстрая, детерминированная область памяти, работающая по принципу LIFO; освобождается автоматически при выходе из метода. Куча — большая область для долгоживущих объектов; очищается сборщиком мусора (GC). Ссылки в куче могут пережить стековый кадр, создавший их.

**Семантика копирования** определяет поведение при передаче аргументов: по умолчанию и value-, и reference-типы передаются **по значению** (копия значения для value-типа, копия ссылки для reference-типа). Ключевое слово `ref`/`out`/`in` меняет семантику на передачу по ссылке.

**Boxing и unboxing.** Когда значимый тип приводится к `object` или интерфейсу, происходит **boxing** — создаётся копия значения в куче, а ссылка на неё возвращается. Обратный процесс — **unboxing** — извлекает значение из коробки. Это дорогие операции (аллокация + копирование), создающие нагрузку на GC. Избегайте их там, где можно использовать дженерики.

**Строка — особый ссылочный тип.** `string` ссылочный, но **неизменяемый (immutable)**: любое «изменение» создаёт новый объект. Это даёт иллюзию value-семантики — две переменные с одинаковым литералом безопасно разделяют ссылку. Помните: `==` для строк сравнивает значения, а не ссылки.

**Где что использовать.** `struct` — для небольших, неизменяемых, логически цельных кусков данных (точка, цвет, деньги), когда копирование дёшево. `class` — для объектов с идентичностью, изменяемым состоянием, иерархией наследования. Слишком большой `struct` копируется дорого и вредит производительности.

#### Theory (EN)

In C#, every type falls into one of two broad categories: **value types** and **reference types**. Understanding the distinction is foundational for memory efficiency, performance, and predictable code behavior.

**Value types** include all numeric primitives (`int`, `double`, `bool`, `char`), enumerations (`enum`), and structures (`struct`, including `DateTime`, `Guid`, tuples). A variable of a value type stores the data itself. When you assign one variable to another, a **bitwise copy** is created — two independent variables holding identical content. Value types typically live on the **stack** when they are local variables, or **inline** — embedded directly inside the containing object — when they are fields of a reference type. The defining property is copy-by-value semantics.

**Reference types** are `class`, `interface`, `delegate`, `array`, `string`, and `object`. A variable of a reference type does not hold the data; it holds an **address** into the managed heap where the data actually resides. On assignment, the reference is copied, not the object: two variables point to the same heap object. A mutation through one variable is visible through the other.

**The "bearer bond vs safe address" analogy.** A value type is like a bearer bond you hold in your hand: handing it to a colleague means giving up the original (really, an exact copy), and your copy stays independent of theirs. A reference type is like the address of a bank safe: you can hand the address to ten people, but there is still only one safe — anyone with the address can put money in, and everyone else sees it.

**Stack and heap.** The stack is a fast, deterministic, LIFO memory region that is reclaimed automatically when a method exits. The heap is a large region for long-lived objects, cleaned by the garbage collector (GC). A heap reference can outlive the stack frame that created it.

**Copy semantics** drives argument passing: by default, both value and reference types are passed **by value** (a copy of the value for value types, a copy of the reference for reference types). The `ref`/`out`/`in` keywords switch to pass-by-reference semantics.

**Boxing and unboxing.** When a value type is converted to `object` or an interface, **boxing** occurs — a copy of the value is allocated on the heap and a reference to it is returned. The reverse, **unboxing**, extracts the value back out. These are expensive operations (allocation + copy) that pressure the GC. Prefer generics wherever possible to avoid them.

**String is a special reference type.** `string` is reference-typed but **immutable**: any "change" creates a new object, giving the illusion of value semantics — two variables holding the same literal safely share a reference. Remember: `==` on strings compares values, not references.

**When to use which.** Use `struct` for small, immutable, logically cohesive chunks of data (a point, a color, money) where copying is cheap. Use `class` for objects with identity, mutable state, and inheritance hierarchies. An oversized `struct` is expensive to copy and hurts performance.

#### Пример кода / Code Example

```csharp
// C# 12 / .NET 8 — value vs reference types, stack vs heap, boxing
// Демонстрация семантики копирования, boxing/unboxing и immutable string

using System;

// Значимый тип (record struct) — копируется побитово / Value type: bitwise copy
// record struct (C# 10+) поддерживает with-expressions, == и авто-Equals/GetHashCode,
// в отличие от обычного struct. / Unlike a plain struct, a record struct supports
// with-expressions, ==, and auto-generated Equals/GetHashCode.
public readonly record struct Money(decimal Amount, string Currency)
{
    public Money Add(Money other) =>
        Currency == other.Currency
            ? this with { Amount = Amount + other.Amount }   // with-expression: новая копия / new copy
            : throw new InvalidOperationException(
                $"Валюты не совпадают: {Currency} vs {other.Currency}");
}

// Ссылочный тип (class) — копируется ссылка / Reference type: reference copy
public class BankAccount
{
    public string Owner { get; set; }
    public Money Balance { get; private set; }

    public BankAccount(string owner, Money initial) =>
        (Owner, Balance) = (owner, initial);

    public void Deposit(Money amount) => Balance = Balance.Add(amount);
}

var a = new Money(100m, "USD");   // value-переменная в стеке / value var on the stack
var b = a;                        // КОПИЯ: b независим от a / COPY: b independent of a
b = b with { Amount = 200m };     // with создаёт копию с новым Amount / with creates a copy with new Amount
Console.WriteLine($"a={a.Amount}, b={b.Amount}");   // a=100, b=200

var acc1 = new BankAccount("Alice", new Money(50m, "USD"));
var acc2 = acc1;                  // ОДНА ССЫЛКА: тот же объект / SAME reference: same object
acc2.Deposit(new Money(30m, "USD"));
Console.WriteLine($"acc1={acc1.Balance.Amount}");    // 80 — изменение видно через acc1

// Boxing: value type -> object -> куча / Value type boxed onto the heap
int n = 42;
object boxed = n;                 // BOXING: аллокация в куче / heap allocation
int unboxed = (int)boxed;         // UNBOXING: извлечение значения / extract value
Console.WriteLine($"boxed={boxed}, unboxed={unboxed}");

// Дженерики вместо boxing для производительности / Generics avoid boxing
List<int> numbers = [1, 2, 3, 4, 5];   // collection-initializer, no boxing
int sum = 0;
foreach (var x in numbers) sum += x;    // value-путь, без аллокаций / no allocation

// String: ссылочный, но immutable / reference-typed but immutable
string s1 = "hello";
string s2 = s1;                   // та же ссылка на интернированный литерал / shared interned ref
s2 = s2.ToUpper();                // создаётся НОВЫЙ объект / creates a NEW object
Console.WriteLine($"s1={s1}, s2={s2}");   // s1=hello, s2=HELLO

// Pattern matching: различаем value vs reference в реальном коде
string Describe(object obj) => obj switch
{
    int i when i > 0      => $"Положительное целое: {i} (boxed value)",
    string s              => $"Строка длины {s.Length}: «{s}»",
    Money m               => $"{m.Amount} {m.Currency} (struct, boxed)",
    BankAccount { Owner: var o } => $"Счёт владельца {o}",
    null                  => "null",
    _                     => $"Другое: {obj}"
};

Console.WriteLine(Describe(n));
Console.WriteLine(Describe(s1));
Console.WriteLine(Describe(a));
Console.WriteLine(Describe(acc1));
```

#### Best Practices

- Используйте `readonly struct` для небольших (≤ 16 байт) неизменяемых данных — копирование дёшево, нет аллокаций в куче.
- Делайте `struct` иммутабельными; изменяемые `struct` порождают тонкие баги из-за копирования при каждом присваивании.
- Передавайте большие структуры через `in`, чтобы избежать лишнего копирования без права изменения.
- Используйте `record struct` (C# 10+) для value-типов с автоматической `Equals`/`GetHashCode` и `with`-выражениями.
- Избегайте boxing: применяйте дженерики (`List<int>`, а не `ArrayList`), перегрузки `ToString(string format?)` вместо `object`-параметров.

- Use `readonly struct` for small (≤ 16 bytes) immutable data — cheap to copy, no heap allocation.
- Keep `struct`s immutable; mutable `struct`s breed subtle bugs because every assignment copies.
- Pass large structs via `in` to avoid redundant copies without granting write access.
- Use `record struct` (C# 10+) for value types with auto-generated `Equals`/`GetHashCode` and `with`-expressions.
- Avoid boxing: prefer generics (`List<int>` over `ArrayList`) and typed overloads over `object` parameters.

#### Частые ошибки / Common Mistakes

- Изменяемый `struct`, мутируемый через свойство в `List<T>` → `list[i].X = 5;` не компилируется (возвращается копия) → делайте `struct` иммутабельным и заменяйте целиком: `list[i] = list[i] with { X = 5 };`.
- Сравнение ссылок вместо значений для `string` через `ReferenceEquals` → используйте `==` или `string.Equals` — сравнение по содержимому.
- Неявный boxing в цикле (`foreach (object o in intArray)`) → типизируйте цикл `foreach (int i in intArray)`, чтобы не аллоцировать.
- Передача большого `struct` по значению в горячем методе → `in`-параметр или `ref readonly`.
- Ожидание, что `ref`-параметр меняет value-семантику на reference-семантику для всего объекта → `ref` работает только в пределах вызова; для постоянной «алиасности» используйте поля или `ref struct`.
- Уверенность, что `decimal`/`DateTime` живут в куче → это value-типы; в кучу попадают только при boxing или как поля class-объекта.

- Mutable `struct` mutated via a property in `List<T>` → `list[i].X = 5;` won't compile (a copy is returned) → make the `struct` immutable and replace wholesale: `list[i] = list[i] with { X = 5 };`.
- Reference comparison instead of value comparison for `string` via `ReferenceEquals` → use `==` or `string.Equals` for content comparison.
- Implicit boxing in a loop (`foreach (object o in intArray)`) → type the loop as `foreach (int i in intArray)` to avoid allocations.
- Passing a large `struct` by value in a hot method → use an `in` parameter or `ref readonly`.
- Expecting `ref` to turn value semantics into reference semantics permanently → `ref` is scoped to the call; for persistent aliasing use fields or `ref struct`.
- Assuming `decimal`/`DateTime` live on the heap → they are value types; they reach the heap only via boxing or as fields of a class object.
