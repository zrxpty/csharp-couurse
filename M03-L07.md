### Урок M03-L07: Перегрузка методов, область видимости / Method overloading, scope

**Время / Time:** 30 мин теория + 45 мин практика

#### Теория / Theory

**Перегрузка методов.** В C# можно объявить в одном классе несколько методов с **одинаковым именем**, если у них **разные сигнатуры**. Сигнатура складывается из числа, типов и порядка параметров (модификаторы `ref/out/in` тоже учитываются). Возвращаемый тип в сигнатуру **не входит**, поэтому два метода, отличающихся только типом возвращаемого значения, компилятор не различит. Аналогия: слово «печь» в русском языке означает и глагол («печь пироги»), и существительное («русская печь») — значение выбирается по контексту. Так же компилятор по аргументам вызова подбирает нужную перегрузку.

**Зачем перегружать.** Это даёт единый словарь действий: `Print(int)`, `Print(string)`, `Print(string, int)` — везде одно имя, разная реализация. Пользователю класса не нужно помнить `PrintInt`, `PrintStr`, `PrintStrNTimes`. Альтернатива — значения по умолчанию и `params` — иногда удобнее, но перегрузки дают строго типизированные ветки и разные тела.

**Разрешение перегрузки (overload resolution).** Компилятор проходит по кандидату и выбирает «наилучший» метод. Сначала отсеиваются те, куда аргументы не преобразуются вообще. Из оставшихся побеждает тот, чьи параметры «ближе» к типам аргументов. Правила лучшей конверсии: `int` → `int` лучше, чем `int` → `double`; `string` → `string` лучше, чем `string` → `object`; `int` → `long` лучше, чем `int` → `double`. Если преобразование требует снятия с ограничений или неточного приведения (`int` → `int?`), вес снижается.

**Неоднозначности.** Иногда два кандидата одинаково хороши — и компилятор выдаёт ошибку `CS0121: The call is ambiguous`. Классический пример: перегрузки `M(double, int)` и `M(int, double)` при вызове `M(1, 1)` — оба аргумента `int`, в первой перегрузке первый аргумент идёт «дальше» (`int`→`double`), во второй второй — так же, счет равный, победителя нет. Лекарство: явно привести аргумент `M((double)1, 1)` либо добавить более точную перегрузку `M(int, int)`. Динамические аргументы (`dynamic`) откладывают выбор до времени выполнения и могут давать `RuntimeBinderException`.

**Область видимости переменных.** Каждое объявление «живёт» в своём контексте. *Блок* (фигурные скобки внутри метода) — самая узкая область: переменная, объявленная в `if`-блоке, снаружи невидима. *Метод* — параметры и локальные переменные действуют до конца тела. *Класс* — поля и свойства доступны во всех методах класса. Правило простое: имя видно от точки объявления до закрывающей скобки области, где оно объявлено. Переменные нельзя объявить с одинаковым именем в одной и той же области; во вложенных — можно, но это рискованно.

**Затенение (shadowing).** Локальная переменная может совпасть по имени с полем класса. Тогда внутри метода имя ссылается на локаль, «затеняя» поле. Чтобы достать поле, используют `this.field`. Для параметров конструкторов это стандартный приём: `this.name = name;`. Затенение — не ошибка, но источник трудноуловимых багов: читатель думает, что меняет поле, а меняет копию-локаль. Аналогия: два человека в одной комнате с одинаковым именем; оклик «Иван!» реагирует ближайший.

**Local functions (C# 7+).** Метод, объявленный **внутри другого метода**. Виден только в области родительского метода, не засоряет класс. Удобен для вспомогательной логики, рекурсии, валидации, обработки `IEnumerable` (yield). Компилятор может превратить local function в `static` (если она не захватывает локальные переменные родителя) и оптимизировать её как обычный метод. С C# 8 поддерживается модификатор `static` для local function — она не может обращаться к переменным охватывающего метода, что исключает скрытые захваты и ошибки замыкания. Внутри local function можно объявить ещё одну local function.

#### Theory (EN)

**Method overloading.** C# lets a class declare several methods with the **same name** if they have **different signatures**. A signature is the number, types, and order of parameters (modifiers `ref/out/in` count too). The return type is **not** part of the signature, so two methods differing only by return type cannot coexist as overloads. Analogy: the English word "run" means different things in "run a race," "run a program," and "run a business" — meaning is chosen from context. The compiler likewise picks the right overload from the call arguments.

**Why overload.** It gives one vocabulary for one action: `Print(int)`, `Print(string)`, `Print(string, int)` — same name, different bodies. Users don't have to remember `PrintInt`, `PrintStr`, `PrintStrNTimes`. Default parameters and `params` are sometimes cleaner alternatives, but overloads give strictly typed branches and distinct implementations.

**Overload resolution.** The compiler walks the candidate set and selects the "best" method. It first drops candidates whose parameters the arguments can't convert to. Among survivors, the one whose parameters are "closer" to the argument types wins. Better-conversion rules: `int` → `int` beats `int` → `double`; `string` → `string` beats `string` → `object`; `int` → `long` beats `int` → `double`. Conversions that lose precision or add nullability carry less weight.

**Ambiguities.** Sometimes two candidates are equally good — and the compiler emits `CS0121: The call is ambiguous`. Classic case: overloads `M(double, int)` and `M(int, double)` called as `M(1, 1)` — both arguments are `int`, each overload "widens" exactly one argument, so there is no winner. Fixes: cast an argument explicitly `M((double)1, 1)`, or add a more precise overload `M(int, int)`. `dynamic` arguments defer the choice to runtime and may throw `RuntimeBinderException`.

**Variable scope.** Every declaration lives in a context. A *block* (braces inside a method) is the narrowest scope — a variable declared in an `if` block is invisible outside it. A *method* holds parameters and locals until the end of the body. A *class* holds fields and properties available to every method. The rule is simple: a name is visible from its declaration point to the closing brace of its scope. You can't redeclare a name in the same scope; in a nested scope you can, but it's risky.

**Shadowing.** A local can share a name with a class field. Inside the method the name then refers to the local, "shadowing" the field. To reach the field, write `this.field`. For constructor parameters this is idiomatic: `this.name = name;`. Shadowing isn't an error, but it's a source of subtle bugs: the reader thinks they're mutating a field while they're actually touching a local copy. Analogy: two people in a room share a name; the closer one answers to "Alex."

**Local functions (C# 7+).** A method declared **inside another method**. It's visible only within the enclosing method and doesn't pollute the class. Handy for helpers, recursion, validation, and `IEnumerable` (yield) processing. The compiler may lower a local function to a `static` method (when it captures nothing from the parent) and optimize it like any ordinary method. Since C# 8 you can mark a local function `static` — it then cannot touch the enclosing method's locals, eliminating hidden captures and closure bugs. A local function may itself contain another local function.

#### Пример кода / Code Example

```csharp
// C# 12 / .NET 8 — top-level statements
using System;
using System.Collections.Generic;

// Демонстрация перегрузки, разрешения, области видимости, shadowing и local functions.
// Demonstrates overloading, resolution, scope, shadowing, and local functions.

Calculator calc = new();

// Разрешение выбирает Print(int) — точное совпадение лучше, чем int→double.
// Resolution picks Print(int) — exact match beats int→double.
calc.Print(42);
calc.Print("answer");
calc.Print("hi", 3);

// Безопасный вызов с неоднозначными перегрузками — Add(int,int) выигрывает.
// Safe call with potentially ambiguous overloads — Add(int,int) wins.
Console.WriteLine(calc.Add(2, 3));       // 5
Console.WriteLine(calc.Add(2.5, 3.1));   // 5.6 (double overload)

class Calculator
{
    // Поля класса — область видимости «класс».
    // Class fields — "class" scope.
    private int callCount = 0;

    // ---- Перегрузки метода Print / Print overloads ----
    public void Print(int value)        => PrintCore(value.ToString());
    public void Print(string value)     => PrintCore(value);
    public void Print(string value, int times)
    {
        // Локальная переменная value «затеняет»… нет, тут value — параметр.
        // Параметр times в области метода. Поля класса всё ещё доступны.
        // The local 'value' is a parameter here; 'times' is in method scope;
        // class fields are still reachable.
        for (int i = 0; i < times; i++) PrintCore(value);
    }

    private void PrintCore(string text)
    {
        callCount++;
        Console.WriteLine($"[{callCount}] {text}");
    }

    // ---- Перегрузки Add / Add overloads ----
    // Если оставить только Add(double,int) и Add(int,double),
    // вызов Add(1,1) даёт CS0121 ambiguous. Поэтому добавляем Add(int,int).
    // With only Add(double,int) and Add(int,double), Add(1,1) is CS0121 ambiguous.
    // So we add Add(int,int).
    public int Add(int a, int b) => a + b;
    public double Add(double a, int b) => a + b;
    public double Add(int a, double b) => a + b;
    public double Add(double a, double b) => a + b;

    // ---- Local function + shadowing + рекурсия ----
    // ---- Local function + shadowing + recursion ----
    public int Factorial(int n)
    {
        // 'n' параметра затеняется локальной 'n' в блоке ниже — опасно, показываем как НЕ надо.
        // The parameter 'n' is shadowed by a local 'n' below — risky, shown as anti-pattern.
        if (n < 0) throw new ArgumentOutOfRangeException(nameof(n));

        // Local function: видна только внутри Factorial.
        // Local function: visible only inside Factorial.
        int compute(int k)
        {
            // Блок-область для промежуточного результата.
            // Block scope for an intermediate value.
            if (k <= 1) return 1;

            // Рекурсивный вызов другой local function.
            // Recursive call to another local function.
            return k * compute(k - 1);
        }

        // Static local function (C# 8+) — не может захватить 'n' родителя,
        // принимает всё явно через параметры. Защита от скрытых замыканий.
        // Static local function (C# 8+) — cannot capture the parent's 'n';
        // everything is passed explicitly. Guards against hidden closures.
        static int logSafe(int value, int step)
        {
            Console.WriteLine($"  шаг / step {step}: {value}");
            return value;
        }

        int result = compute(n);
        return logSafe(result, n);
    }

    // ---- Shadowing: поле против параметра конструктора-подобной логики ----
    // ---- Shadowing: field vs constructor-like parameter ----
    private string label = "default";

    public void SetLabel(string label)
    {
        // 'label' (параметр) затеняет 'label' (поле). Через this.label берём поле.
        // 'label' (parameter) shadows 'label' (field). Use this.label for the field.
        this.label = label;
        Console.WriteLine($"новый label / new label: {this.label}");
    }
}
```

#### Best Practices

- Держите перегрузки **согласованными по семантике**: все версии `Add` должны складывать, а не одна складывать, другая логировать — иначе имя вводит в заблуждение.
- Предпочитайте `static` local functions, если они не нуждаются в захвате переменных родителя: компилятор генерирует более простой код и вы ловите ошибки захвата на этапе компиляции.
- Не злоупотребляйте затенением: если параметр конструктора совпадает по имени с полем, используйте `this.` явно и последовательно — это идиома, а не ловушка.
- При сомнительном разрешении перегрузки приводите аргументы явно — это документирует намерение и страхует от будущих изменений в наборе перегрузок.
- Keep overloads **semantically consistent**: every `Add` should add, not have one add and another log — otherwise the name misleads.
- Prefer `static` local functions when no capture is needed: the compiler emits simpler code and capture mistakes surface at compile time.
- Don't lean on shadowing for style: when a constructor parameter matches a field name, use `this.` consistently — it's an idiom, not a trap.
- When overload resolution looks fragile, cast arguments explicitly — it documents intent and survives future overload additions.

#### Частые ошибки / Common Mistakes

- Перегрузка по возвращаемому типу → это невозможно в C#: компилятор не различит вызовы. Различайте по параметрам или используйте разные имена.
- `M(int, double)` и `M(double, int)` при вызове `M(1, 1)` → CS0121 ambiguous. Добавьте `M(int, int)` или явно приведите аргумент.
- Объявление переменной в `if`-блоке и использование её снаружи → ошибка компиляции «name does not exist». Выносите переменную в охватывающую область, если она нужна позже.
- Локальная переменная с тем же именем, что и поле, без `this.` → тихо затеняет поле, баги в логике. Всегда `this.field` для доступа к полю при совпадении имён.
- Использование `dynamic` для «универсального» метода вместо перегрузок → потеря проверки типов на этапе компиляции и возможный `RuntimeBinderException`.
- Overloading by return type → impossible in C#: calls can't be distinguished. Differentiate by parameters or use distinct names.
- `M(int, double)` and `M(double, int)` called as `M(1, 1)` → CS0121 ambiguous. Add `M(int, int)` or cast an argument explicitly.
- Declaring a variable inside an `if` block and using it outside → "name does not exist" compile error. Move it to the enclosing scope when needed later.
- A local with the same name as a field, without `this.` → silently shadows the field, logic bugs. Always use `this.field` to reach the field on name clash.
- Using `dynamic` for a "universal" method instead of overloads → loses compile-time type checking and may throw `RuntimeBinderException`.
